## Fixed

### C1 — app-bought gift cards had no redemption code

**Was:** `issue_gift_card` / `issue_session_card` never wrote `vouchers.voucher_code`,
and the confirmation route hashed 24 random bytes and discarded the plaintext. A
card bought through checkout could be scanned but not redeemed, because
`redeem_voucher_by_code` resolves a card by its code only. The seeded demo cards
had codes, which is why a counter test passed.

**Now:** `supabase/migrations/0131_checkout_voucher_codes.sql` generates a
human-readable code inside both issue functions, stores it with a matching
`card_code_hash`, backfills vouchers issued without a code, and adds
`redeem_voucher_by_id`. The vendor scanner in `web/lib/actions/vendor.ts` falls
back to the by-id RPC when a voucher has no code, and the wallet shows the code
under the QR.

**Verified:** migration applied; typecheck and 65 unit tests pass. **Not yet
verified end to end** — needs one MyFatoorah test-mode purchase redeemed at the
counter.

### C3 — partial and partner refunds were processed incorrectly

**Was:** the partner branch of `myfatoorah_payment_refunded` was unreachable
(`elsif p.vendor_id is null` inside a block that required `p.vendor_id is not
null`), and any completed refund voided every voucher and debited the full order
total.

**Now:** `0134_refunds_per_seller.sql` reverses exactly the refunded amount,
splits it across the order's vendors and partners in one proportional
allocation, applies the reversal once per refund reference, keeps partially
refunded orders paid with their vouchers alive, and voids only on a full refund.
`web/lib/actions/admin-payments.ts` now sends every supplier allocation instead
of the first. `0135_partial_refund_reduces_card_value.sql` takes each seller's
refunded share off its monetary cards through the voucher ledger, never below
zero, via a trigger on `financial_ledger` so every refund path is covered.

**Verified:** migrations applied; typecheck and tests pass. No real refund has
been exercised yet.

### M4 — one vendor was credited the whole multi-vendor order

**Was:** `myfatoorah_payment_confirmed` credited the first order item's vendor
with the entire order total.

**Now:** `0133_split_vendor_ledger_per_supplier.sql` credits each vendor and
partner its own share, and raises `ledger_allocation_mismatch` rather than
confirming a paid order whose allocation does not add up.

**Verified:** applied. Watch `/admin/orders` for unconfirmed payments if a
product is deleted between checkout and payment.

### Basket contributions were free

**Was:** `basket_contribute` wrote a paid line into the shared basket without any
payment.

**Now:** `supabase/functions/create-basket-payment/index.ts` creates a real
MyFatoorah invoice (JWT-authenticated, prices computed server-side, idempotent
per attempt). `0132_basket_payments.sql` adds `orders.basket_id` and
`gift_basket_items.order_item_id` and a `basket_fulfill_from_payment` RPC, and
`web/app/api/merchant-payment/confirm/route.ts` routes paid basket orders to it
instead of issuing vouchers. The app's contribute screen now pays, then follows
the existing processing handoff.

**Verified:** function deployed and ACTIVE; build passes. **Not yet verified end
to end.**

### Dishonest payment UI

**Was:** the mobile payment-methods screen presented a card form, saved cards and
Apple/Google Wallet buttons that were never wired to anything.

**Now:** it explains that payment happens on MyFatoorah's hosted page, the fake
card form and wallet buttons are gone, and the card detail screen shows the real
redemption code. New strings added in English and Arabic.

### C4 — webhook confirmation rejected because of two secret names

**Was:** `payment-webhook` signs its confirmation call with
`INTERNAL_API_KEY` when that secret exists, and it does exist in production,
while `/api/merchant-payment/confirm` accepted only `SUPABASE_SERVICE_ROLE_KEY`.
Every webhook confirmation returned 401, the webhook threw
`confirmation_failed`, and MyFatoorah's retries never issued a card. Only a
customer returning through the browser callback got their card, so "paid but no
card" appeared whenever someone closed the tab.

**Now:** the confirm route accepts either `INTERNAL_API_KEY` or
`SUPABASE_SERVICE_ROLE_KEY`, compares with a constant-time digest match, and logs
a clear error when neither is configured.

**Verified:** typecheck and web build pass. **Still needs a deploy** of the web
app to take effect, then one test-mode purchase with the browser closed to prove
the webhook path issues the card on its own.

### C2 — vendors and partners saw QAR 0.00 on their own financial pages

**Was:** `financial_ledger` had a single policy, `for select using
(is_admin())`, and `vendor_financial_balances` / `partner_financial_balances`
are `security_invoker`, so a vendor or partner querying its own money got zero
rows. On top of that, `can_see_order` only recognised buyers, admins and the
item's vendor, and there was no `order_items` policy for partner-owned
catalogue products, so a partner could not see the orders behind the entries
it would be paid for.

**Now:** `0136_owner_ledger_and_partner_order_reads.sql` lets a business read
its own ledger rows — `is_vendor_member(vendor_id)` or
`is_enterprise_member(partner_id)`, matching the fact that the financial page
is reachable by every team member — while inserts, updates and deletes stay
closed and the append-only trigger still blocks mutation. Partners gain read
access to the orders that contain their own products, and to those order lines
only, never another seller's lines on the same order. Two indexes
(`vendor_id, created_at desc` and `partner_id, created_at desc`) back the page's
"latest 100" query.

**Verified:** migration applied to production, then checked with an RLS probe as
an authenticated member of each business. A vendor member saw its own probe row
and 0 rows of another vendor's. A partner member saw its own ledger row
(total 777) and, out of 10 orders in the database, exactly the 1 order and 1
order line that belong to its products. Every probe ran in a transaction that
was rolled back; `financial_ledger` is still empty.

**Not verified:** the rendered pages, which need a browser session with a real
account. The data access beneath them is now proven.

### C6 — vendors could rewrite their own voucher rows

**Was:** `vouchers_update_vendor` granted `for update` to `can_manage_vendor(...)`
with no column limits, so a vendor could set `status`, `remaining_value_minor`,
`voucher_code`, `expires_at`, `buyer_id` or `claimed_by` on a sold card. The
ledger stayed truthful because redemption reads the append-only ledger, but a
vendor could void a customer's card or desynchronise the displayed balance.

**Now:** `0137_restrict_voucher_updates_to_admin.sql` drops that policy. No
vendor flow writes the table directly — redemption goes through
`redeem_voucher_by_code` / `redeem_voucher_by_id`, and delivery, bulk and admin
tools use the service role or an admin session — so there is no column a vendor
legitimately writes here. The admin void/expire action in
`web/lib/actions/admin.ts` used the admin branch of the old policy, so it now has
its own explicit `vouchers_update_admin` policy.

**Verified:** migration applied, then probed as an authenticated vendor member:
an update setting `status = 'void'`, `remaining_value_minor = 0` and
`voucher_code = 'HACKED'` changed **0 rows**, as did a `delivery_status` update.
The same voucher updated as an admin changed 1 row. Both probes rolled back; the
card is still `issued`, code intact, 2500 minor remaining.

### C5 — exposure and stock checks could be raced

**Was:** `create-payment` read `vendor_outstanding_minor()`, compared it to the
vendor's cap, and only then created the order. Outstanding is derived from
issued vouchers, so a concurrent request was invisible: N simultaneous checkouts
all passed, all were invoiced, and once paid the vendor's unredeemed balance
blew past the cap. `bulk_checkout_create` compared `v_qty` to
`available_quantity` but only reserved stock much later in `fulfill_bulk_order`,
whose conditional decrement ignored a zero-row result — both buyers paid and the
vendor was oversold.

**Now:** `0138_serialise_exposure_and_stock.sql`.

- `order_items_exposure_guard` (BEFORE INSERT) takes a `for update` lock on the
  vendor row, then checks live vouchers plus orders pending payment from the last
  24h (abandoned invoices must not hold capacity forever). Concurrent inserts
  serialise on the vendor row and the loser sees the winner's order. Bulk
  checkouts are exempt: their capacity model is stock, and a retail unredeemed
  cap would reject legitimate 1,000-card orders.
- `bulk_checkout_create` reserves stock with one conditional UPDATE
  (`available_quantity >= v_qty`) and records `bulk_orders.stock_reserved`;
  `fulfill_bulk_order` no longer decrements a reservation (and now raises if a
  legacy zero-row decrement happens); cancelling a reserved order returns the
  quantity.
- Both payment functions map the trigger's `vendor_exposure_limit_reached` to a
  409 instead of a 500.

**Verified** against production, with every probe value restored afterwards:

| probe | result |
|---|---|
| vendor cap = outstanding + 3500; A commits a 3000 order holding the lock 4s, B starts 1s later | B **waited 4530 ms**, then refused: `used=238500 limit=239000 requested=3000` |
| cap = outstanding + 500; 400 order | accepted |
| same cap; 600 order | refused |
| stock 30; A reserves 20; B asks for 20 | A accepted, stock 10; B refused `insufficient_quantity` |
| buyer cancels A's reserved order | stock back to 30, `stock_reserved = false` |

Probes were cleaned up; the test vendor is back to `pending`/not eligible, cap
0, and the offer back to 440 units.

### M1 — the public login gate could lock out an address and reset any counter

**Was:** `auth-gate` is a public Edge Function with the service role behind it,
and it trusted both the `identifier` and the `ip` in the request body. Eight
`record` calls with `success: false` locked any e-mail out of the mobile app; one
`record` call with `success: true` cleared any account's counter. The web app was
never exposed this way — it calls the ledger functions from a server action with
a derived IP — so the hole was the mobile app's direct calls.

**Now:** the function scopes every counter to `mobile-login:<email>|<source>`,
where the source comes from platform request headers (`x-real-ip`,
`cf-connecting-ip`, or the right-most `x-forwarded-for` entry), never the body. A
stranger can only exhaust their own budget for an address, so the victim's
network is unaffected. Clearing requires the `Authorization: Bearer` token of
the session that just signed in and is only accepted when that token's e-mail is
the identifier being cleared — no token is a 401, a foreign or invalid token is a
403, and neither touches the ledger. Identifiers are validated as e-mail
addresses before use, so the ledger cannot be polluted with junk keys. The mobile
app now sends the session token on the success report.

**Verified** against the deployed function:

| probe | result |
|---|---|
| `identifier: "not-an-email"` | 400 `invalid_identifier` |
| fresh address | `{allowed: true}` |
| success report with no token | 401 `proof_required` |
| success report with a bogus token | 403 `proof_invalid` |
| eight failure reports, then check | 429 `{allowed: false}` |
| eight failures recorded against a different network's bucket, then check here | 200 `{allowed: true}` |
| ledger key after eight failures | `mobile-login:<email>|208.72.218.131` — the spoofed `x-forwarded-for: 203.0.113.9` was ignored |

Probe rows were deleted. The positive path (a real session token clearing its own
counter) was not exercised end to end, because that needs a working account
password; the 401/403 refusals are the security-critical half.

### M2 — claim lookups had no limit (the index was already there)

**Index:** not missing in the current schema. `vouchers.claim_token_hash` kept its
`unique` from `0001` through the `gift_cards` → `vouchers` rename, so
`gift_cards_claim_token_hash_key` exists and `EXPLAIN` shows
`Index Scan using gift_cards_claim_token_hash_key`. No index was added; adding a
second one would only cost writes.

**Limit:** `claim_card` (the actual claim) already throttles through
`claim_attempts`. `claim_preview`, which is callable by `anon` and runs on every
claim-page load, had no limiter at all. `0140` adds two
buckets in the existing `auth_attempts` ledger: 30 lookups / 10 min per token
hash, and 120 / 10 min per caller address when PostgREST's `request.headers`
carries one (it is skipped rather than pooled into a global bucket if not, so
innocent users are never throttled together).

**A bug found while testing:** the first version raised `invalid token` *after*
inserting the counter row, and the raise rolled the whole statement back — so
guessing never accumulated and the limit could not fire for the case that
matters. `0141` makes an unknown token return no rows instead (both callers
already treat "error or no data" as not found) and marks the function volatile,
since it writes.

**Verified:** 30 calls with one token allowed and the 31st refused with
`too_many_requests`; a different token in the same minute still answers; a real
voucher inserted with a known token hash resolved through `claim_preview`
(rolled back). Probe ledger rows deleted.

**Per-caller limit, follow-up (`0142` + `supabase/functions/claim-preview`).**
The per-address bucket was only enforceable if the caller cannot bypass it, and
PostgREST does not guarantee a forwarding header. `claim_preview` is now
service-role only (the anon-callable overload is dropped), takes the caller
address explicitly, and has two trusted callers:

- `supabase/functions/claim-preview` — the mobile app posts the token here; the
  runtime supplies the address it observed. Deployed without JWT verification,
  like `auth-gate`.
- `web/app/claim/[token]/page.tsx` — server component, so Next supplies the
  visitor's `x-forwarded-for` and the RPC runs with the admin client.

**Verified after the move:** `anon` has no execute privilege on
`claim_preview(text,text)`, `service_role` does, and exactly one overload exists.
A real voucher resolved through the new signature with a supplied source
(rolled back). The deployed function returned `{gift: null}`/200 for an unknown
and for a too-short token, and 429 `too_many_requests` on the 31st lookup of one
token. The ledger showed `claim-ip:208.72.218.131` — a real address, taken from
the runtime rather than the client. Probe rows deleted; root `tsc`, web `tsc` and
`next build` pass.

Compatibility note: mobile builds that still call the RPC directly lose the claim
preview (they see "not found") until they pick up the new app bundle; claiming
itself is unaffected because `claim_voucher`/`claim_card` were not changed.

### M3 — the mobile session sat in AsyncStorage in plaintext

**Was:** `src/lib/supabase.ts` handed Supabase `AsyncStorage` as the session
store. The refresh token — bearer-equivalent for the account — was readable by
anything with filesystem access on a rooted or jailbroken device, and included
in Android auto-backup.

**Now:** `src/lib/secure-storage.ts` is the adapter. On iOS and Android it writes
to the Keychain / Keystore-backed encrypted preferences through
`expo-secure-store` (installed as `~58.0.3` with its config plugin, which also
excludes the entries from Android backup). Two details that matter:

- **Chunking.** Native stores historically reject values above ~2 KB and a
  Supabase session is larger, so values are split into 1800-character chunks
  with a counter key and rejoined on read; stale chunks are deleted on rewrite.
- **Web and migration.** `expo-secure-store` has no web implementation, so the web
  build keeps AsyncStorage. An existing plaintext session is moved into the
  secure store the first time it is read and the old copy removed, so upgrading
  users stay signed in.

**Verified:** `tsc`, eslint on the changed files and `npm test` (65/65) pass. Not
verified on a device: no simulator here, so the Keychain round-trip, the chunk
reassembly above 2 KB and the one-time migration are review-only.

### M9 — the refund webhook booked whatever amount the payload claimed

**Was:** `REFUND_STATUS_CHANGED` took `Amount.ValueInBaseCurrency`, multiplied
by 100 and passed it to `myfatoorah_payment_refunded` without comparing it to the
invoice we had recorded. The signature proves the event came from MyFatoorah, not
that the number is right — a provider-side currency mix-up or rounding error
would have been posted into the refund ledger and split across sellers.

**Now:** the webhook loads `myfatoorah_payments` for the referenced invoice and
compares the claimed refund to `amount_minor` before calling the RPC. A refund
larger than the recorded payment, a missing/zero amount, or an invoice we never
recorded is logged with the ids and amounts, marked processed (so MyFatoorah does
not retry a decision that will not change) and skipped with
`reason: refund_amount_mismatch`. The cumulative cap inside
`myfatoorah_payment_refunded` (`refund_exceeds_payment`) still applies to partial
refunds.

**Verified:** the function deploys and an unsigned refund event is rejected with
401 `invalid_signature`. The comparison branch itself was not exercised
end-to-end because signing a webhook needs `MYFATOORAH_WEBHOOK_SECRET`, which is
not available here; that path is review-only.

### M6 — failed and cancelled payments were never recorded on the payment row

**Was:** `PAYMENT_STATUS_CHANGED` mapped failed events onto `orders` only. The
`myfatoorah_payments` row stayed `pending` forever, so any reconciliation against
MyFatoorah showed invoices open on our side that the provider had closed — and a
later refund or dispute had no payment-level state to reason about.

**Now:** the same branch updates `myfatoorah_payments` by `invoice_id`:
`failed` for a failed transaction, `cancelled` for a cancelled or expired
invoice (the payment column is text, so it can hold that precision), and
`refunded` for a refunded invoice. A paid payment is never downgraded: the
failed/cancelled update is filtered with `payment_status <> 'paid'`, while
`refunded` intentionally still applies to a paid row. If the update fails the
function throws, so MyFatoorah retries rather than leaving the two systems
diverged. Orders keep using `failed` for cancellations because `order_status`
has no `cancelled` value.

**Verified** at SQL level, in a rolled-back transaction: a pending payment moved
to `failed`; a paid payment stayed `paid` when a cancelled update ran; and a
`refunded` update applied to the paid row. No probe rows left behind. The webhook
handler itself was not exercised with a signed event — `MYFATOORAH_WEBHOOK_SECRET`
is not available here; an unsigned request still returns 401.

### M5 — the stored running balance was computed without serialisation

**Was:** `myfatoorah_financial_entry` (and the partner twin) read
`sum(amount_minor)` for the seller and then inserted a row carrying
`balance_after_minor`. Two concurrent writes both read the same starting total,
so the second row stored a balance that was short by the first amount. The
balance *views* stayed correct because they sum the immutable ledger; the stored
column — used by exports and statements — could disagree with the account.

**Now:** `0143` recreates both functions with a transaction-scoped advisory lock
keyed on the seller (`financial_ledger:vendor:<id>` / `:partner:<id>`) taken
before the sum and the insert. The second writer waits, then sees the first row.
An advisory lock is used rather than `for update` on the vendor row because the
exposure trigger on `order_items` also locks that row, and mixing the two lock
spaces invites deadlocks between checkout and settlement. The lock releases with
the transaction, including on rollback.

**Verified** against production, then cleaned up: writer A inserted 1000 and
held the lock 4s; writer B started 1s later, **waited 4,324 ms**, and returned
2000. Stored rows read `1000 → 1000` and `1000 → 2000`, which is the sequence the
old code could not produce (it would have stored 1000 twice). Probe rows were
deleted with the append-only trigger temporarily disabled and re-enabled; the
ledger is back to 0 rows and `financial_ledger_append_only` is `O` (enabled). No
backfill was needed — the ledger held no rows when the lock was added.

### M8 — the Supabase project ref was hardcoded in the web app

**Was:** `web/lib/i18n/ai.ts` printed a literal
`https://rxrrbznwnsgzpinirzme.supabase.co/functions/v1/mcp` in both the English
and Arabic copy, `web/next.config.ts` allowlisted that exact host for the image
optimiser, and `web/components/OptimizedImage.tsx` listed it again. Moving the
project, or pointing a preview at another one, would have silently published a
stale endpoint and blocked its images.

**Now:** all three derive the host from `NEXT_PUBLIC_SUPABASE_URL` — the same
variable the Supabase clients already require — with the literal removed. The
MCP endpoint is built from it once per module load; the image allowlist entry is
omitted when the variable is unset; `OptimizedImage` accepts the configured host
plus its existing `*.supabase.co` rule. The connection-details block on
`/ai-gift-cards` is hidden when the endpoint is empty rather than printing a
blank URL.

**Verified:** `tsc` and `next build` pass. A build with
`NEXT_PUBLIC_SUPABASE_URL=https://testproject1234567890.supabase.co` produced the
chunk expression `w="https://testproject1234567890.supabase.co" … x = w ?
`${w}/functions/v1/mcp` : ""`, and the generated `images-manifest.json` listed
that host — so both the copy and the optimiser allowlist follow configuration.
No occurrence of the production ref remains in `web/**/*.ts(x)`. A runtime render
check was not possible here: the page creates a Supabase client and this sandbox
has no anon key, so `next start` returns 500 before rendering.

### M7 — the admin export fetched vendor-supplied URLs

**Was:** the admin "download all vendor files" route read
`vendor_documents.file_url` — a value that originates with the vendor — and
passed it straight to `fetch()` from inside the deployment. Admin-only and the
response body is only zipped into the download, which is why this was medium,
but a stored `http://169.254.169.254/…` or an internal hostname would have been
requested by the server.

**Now:** `isOwnStorageUrl()` accepts only `https://` URLs on the host in
`NEXT_PUBLIC_SUPABASE_URL` whose path starts `/storage/v1/object/` — i.e. our own
public storage. Everything else is skipped silently, like any other missing
document. The request also sets `redirect: 'manual'` and accepts only 2xx, so an
allowed host cannot bounce the fetch to an internal address.

**Verified:** `tsc`, eslint on the route and `next build` pass, and
`vendor_documents` holds no rows in production (checked), so the stricter rule
cannot break existing downloads. The predicate itself was not exercised with a
crafted row; the route needs an admin session and real stored documents.

### Money-path tests — and the two defects they found

**What was missing:** no test touched SQL, so every bug fixed above had been
proven only by ad-hoc probes that no longer exist. Only 65 unit tests covered
the client-side helpers.

**What exists now:** `tests/db/` runs the real RPCs against a database with the
migrations applied — there is nothing to mock, the money path *is* SQL.
`tests/db/harness.ts` connects to `TEST_DATABASE_URL`, opens a transaction, and
rolls it back unconditionally, so fixtures and money movements are never left
behind even when an assertion fails; `actAs()` sets `role` and
`request.jwt.claims` the way PostgREST does so RLS is exercised, not bypassed.

Seven tests: payment → credit → issue → redeem to zero; webhook and fulfilment
replay staying idempotent; a seller refused another seller's voucher; a voucher
hidden from other buyers and sellers; confirmation refusing an order line that
belongs to nobody; the ledger entry's direction and running balance; and
counter redemption by typed code.

```bash
TEST_DATABASE_URL=postgresql://... npm run test:db
```

Without `TEST_DATABASE_URL` the suite is skipped, so `npm test` stays
credentials-free.

**Result:** 7/7 pass against production (rolled back; `auth.users`,
`financial_ledger`, `vouchers` and `myfatoorah_payments` verified unchanged
afterwards).

**Two production defects the suite found immediately:**

- **`0144` — payment confirmation could not succeed at all.** `0133` grouped
  each seller's lines with `sum(oi.total_minor)`, which Postgres types as
  `numeric`, and passed it to `myfatoorah_financial_entry(…, bigint, …)`.
  Postgres does not implicitly cast `numeric` to `bigint` when resolving a
  function, so every confirmation of an order with items died with
  `function public.myfatoorah_financial_entry(uuid, uuid, unknown, numeric, text, jsonb) does not exist`
  before crediting anyone. The allocation guard never ran and the order stayed
  unpaid — a webhook 500 on the first real payment. `0144` adds the `::bigint`
  casts. No customer had been affected: `myfatoorah_payments` is empty.
- **`0145` — the ledger labelled every row `QAR`.** Both entry helpers wrote a
  literal `'QAR'` for a marketplace that sells in KWD. `0145` takes the
  currency from the order, falling back to `KWD` for legacy rows.

Both migrations are applied to production.

### No Content Security Policy

**Was:** `web/next.config.ts` sent five security headers but no CSP, so any
XSS — or any third-party script added to a page — ran unrestricted, and nothing
limited where the app may send its Supabase requests or be framed from.

**Now:** the config sends a `Content-Security-Policy` on every response:
`default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors
'none'`, `frame-src 'none'`, `form-action 'self'`, `manifest-src 'self'`.
`connect-src` is `'self'` plus the `https://` and `wss://` host derived from
`NEXT_PUBLIC_SUPABASE_URL`, so a preview or a moved project needs no code edit;
`style-src` adds `fonts.googleapis.com` and `font-src` adds `fonts.gstatic.com`
for the Figtree import, and `img-src` allows `https:` because vendor logos and
ad creatives are arbitrary URLs rendered by plain `<img>`.

`script-src` keeps `'unsafe-inline'` because Next emits its hydration bootstrap
as inline script. A strict policy needs a per-request nonce minted in
`web/proxy.ts`, which forces dynamic rendering on every matched route — a
hosting decision, so it is not mixed into this fix. `script-src-attr 'none'`
blocks inline event handlers in the meantime, which React does not use.

**Verified:** `tsc` and `next build` pass; the built server returns the header
on `/` (see below). **Not verified in a browser:** no anon key in this sandbox,
so authenticated and data pages cannot be rendered to watch for CSP violations
in the console. The directives were chosen by reading the code — Google Fonts
import, `<img>` fallback hosts, inline JSON-LD on `/ai-gift-cards`, no iframes,
no client-side `pdfjs`/`eval` — not by observing a page under enforcement.
